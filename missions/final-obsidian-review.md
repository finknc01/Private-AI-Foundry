# Final — Obsidian Review

## Briefing
Aster Labs’ security committee will approve the environment only if the design survives a hostile design review.

## Challenge
Prepare an architecture packet, then have another person/tool challenge it with 8–10 defensive scenarios: compromised researcher account, lost admin credential, secret exposure, overly broad network path, vulnerable service, malicious-but-non-exploit workload behavior, logging outage, or sensitive artifact copied to the wrong zone.

## Required response
For each scenario state prevention, detection, containment, recovery, residual risk, and evidence from your lab where available.

## Final artifacts
- architecture/trust diagram
- threat model
- control matrix
- segmentation tests
- least-privilege evidence
- secret-handling process
- audit timeline
- PPML boundary analysis
- prioritized residual risks

## Victory condition
Project Obsidian is not “secure because it is private.” It is defensible because its trust assumptions are explicit, controls are testable, and remaining risks are visible.
